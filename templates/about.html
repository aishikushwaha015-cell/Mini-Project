Project introduction

What the project is and how it is meant to be used.

{{ engine_version }}

DRISHTI AI — Digital Risk Identification & Security Through Intelligent AI — is an AI-powered multimodal phishing and brand spoofing detection system built as a Flask web application for examining suspicious links, messages, screenshots, logos and login pages. Each analysis runs locally and returns a score, a risk level and the indicators that contributed to the result. Results can be combined into a single risk assessment, stored as sanitized history and printed as a report.

The dashboard is designed for learning, demonstrations and cautious manual review. It does not visit links, submit forms or upload content to a remote service. A low score is not proof that something is safe, and a high score is not proof of an attack; the output is decision support, not a verdict from an authority.

Processing Local, in memory
Storage Sanitized SQLite metadata
Modules Six analysis paths
Network calls None for detection

Problem statement

Why a local, multi-signal analysis tool is useful.

Phishing arrives through many channels at once: a shortened link in a message, a screenshot of a fake notice, a copied brand logo or a login page that looks almost right. Checking these signals separately is slow, and many online scanners require uploading the original content to a third party.

That creates two problems. First, a single signal can be inconclusive on its own, so users need a way to combine URL, text, image, brand, OCR and form evidence. Second, sensitive content should not have to leave the machine or remain in a database after the check. DRISHTI AI addresses both by running local detectors and persisting only non-sensitive summary metadata.

Project objectives

What the implementation is trying to achieve.

  1. 01
    Analyze multiple phishing signals locally.

    Support URLs, text messages, images, OCR text, brand logos and login-form HTML in one console.

  2. 02
    Make each result understandable.

    Show the score, risk level and the indicators that influenced the analysis instead of a unexplained label.

  3. 03
    Combine evidence without double counting.

    Use fixed, documented weights and report missing or inconclusive modules honestly.

  4. 04
    Preserve privacy by design.

    Keep raw inputs out of SQLite and store only the metadata needed for history and reports.

  5. 05
    Provide a usable security dashboard.

    Offer responsive navigation, searchable history, printable reports and clear error states.

Detection modules

Six independent analysis paths and what each one contributes.

URL Analysis

Extracts structural and lexical features from a submitted URL and runs them through a trained Random Forest model. The URL is never visited.

Machine learning

Text Analysis

Applies local rules for urgency, credential requests, suspicious links, prize wording and similar phishing patterns in a message.

Rule-based

Reads text from a screenshot or image with Tesseract, then reuses the text rules. Images are processed in memory and never saved.

Compares a logo against local reference images using a difference hash and grayscale histogram. Similarity is supporting evidence only.

Inspects pasted or uploaded HTML for credential fields, insecure submissions, hidden inputs and suspicious form actions. Forms are never submitted.

Architecture & detection workflow

How a submitted input becomes a result, a record and a report.

  1. 1
    Input in the browser

    A URL, message, image, logo or HTML snippet is entered or selected in one of the analysis pages.

  2. 2
    Flask route validation

    The route checks type, size and presence, then passes the content to the matching local module.

  3. 3
    Local module analysis

    The module computes a score and indicators. Raw content stays in memory and is never written to disk.

  4. 4
    Result presentation

    The browser displays the verdict, score and reasons. Combined assessment can merge the available module results.

  5. 5
    Sanitized persistence

    A whitelist builds a metadata-only record and writes it to SQLite. Database failures never break detection.

  6. 6
    History and reports

    The overview, history page and printable reports read the sanitized records back from the local database.

No external APIs, cloud inference or remote analytics are part of this workflow. The only optional external dependency is the local Tesseract OCR engine used by the OCR module.

Limitations & future scope

Known boundaries of the current build and possible directions.

{{ icon('alert-circle', 17) }} Current limitations

  • Results are heuristic decision support, not a guarantee that content is safe or malicious.
  • The URL model uses approximate features and its predictions can differ from its original dataset evaluation.
  • Brand analysis depends on reference logos placed locally; with no references it returns an inconclusive result.
  • OCR requires Tesseract to be installed and can struggle with low-quality or stylized images.
  • The text and login-form detectors use fixed rules and may miss novel wording or unusual markup.
  • No accuracy, precision or recall figures are claimed in this interface.
  • The app is a local single-user dashboard without authentication or production hardening.

{{ icon('sparkles', 17) }} Possible future scope

  • Add a curated set of local reference logos for brand comparison.
  • Introduce batch analysis and comparison of several inputs.
  • Offer optional export and import of sanitized history.
  • Expand OCR language support and image pre-processing.
  • Add optional access control for shared machines.
  • Document model evaluation separately from the dashboard.
  • Provide browser-extension or email-client integrations without changing the privacy model.
